# tg-repost — перепост из закрытого чата в закрытый канал

Читает закрытый чат вашим **личным аккаунтом** (Telethon/MTProto) и публикует сообщения
в целевой закрытый канал. Бот здесь не подходит: его нельзя добавить в чат,
к которому нет доступа.

Переносится: текст с исходным форматированием, фото, видео, документы, голосовые,
альбомы — одной пачкой. Служебные сообщения (вход/выход участников) пропускаются.

## Пересылка или копия (`FORWARD`)

`FORWARD=true` (по умолчанию) — **пересылка**: в целевом канале сообщение выглядит
как «Переслано из …». Автор, разметка, медиа и альбомы сохраняются самим Telegram,
файлы не скачиваются и не заливаются заново — быстрее и точнее копии.

`FORWARD=false` — **копия**: сообщение собирается заново, без пометки «переслано».
Это прежнее поведение, к нему возвращаться, если пересылку из источника запретят.
В этом режиме первой строкой поста идёт имя отправителя (жирным) — иначе копия
выглядит так, будто всё написал владелец канала; отключается через `SHOW_AUTHOR=false`,
вид подписи задаётся `AUTHOR_TEMPLATE`. Разметка исходного текста сдвигается корректно:
Telegram считает смещения в UTF-16, и приписанная строка их смещает. При `FORWARD=true`
подпись не нужна и не приписывается.

Переключение — только переменная в `.env`, перезапуск, и всё: обе ветки в коде живые,
состояние (что уже перенесено) общее, дублей при смене режима не будет.

Если в чате-источнике включена защита контента, пересылка невозможна в принципе —
скрипт увидит это на старте (или по ответу `ChatForwardsRestrictedError`), напишет
в лог и сам продолжит копиями.

## Защита от «улетело не в тот чат»

Это главное требование, поэтому проверок пять, и каждая **останавливает** запуск,
а не пишет предупреждение:

1. **Источник ≠ цель.** Оба чата приводятся к каноническому id (`-100…`) и сравниваются.
   Совпадение id или username — аварийный выход, ни одного сообщения не уходит.
2. **Цель не личный чат.** Промах по id пользователя (в т. ч. «Избранное») отсекается.
3. **Сверка по названию.** `DST_TITLE_EXPECTED` — название целевого канала, как вы его
   видите в Telegram. Открылся чат с другим названием → стоп. Это независимая от id
   проверка: чтобы промахнуться, надо ошибиться дважды и одинаково.
4. **Права на публикацию** в целевом канале проверяются до первой отправки.
5. **Привязка пары чатов.** На первом запуске пара «источник → цель» пишется в state.db.
   Если позже `.env` укажет на другую пару — стоп, пока не выставлен `ALLOW_RETARGET=true`.

Сверх этого: `DRY_RUN=true` по умолчанию (первый запуск ничего не отправляет),
одна «канарейка» в целевой канал перед боевым переносом, и повторная сверка
получателя внутри каждой отправки.

Дубликатов не будет: каждое перенесённое сообщение помечается в SQLite,
перезапуск продолжает с места остановки.

## Порядок запуска (по шагам)

### 1. API-ключи

`my.telegram.org` → API development tools → создать приложение → взять `api_id` и `api_hash`.

### 2. Локально: вход и строка сессии

```bash
cd funding-service/tg-repost
python -m venv .venv && .venv\Scripts\activate      # Windows
pip install -r requirements.txt
cp .env.example .env        # вписать TG_API_ID и TG_API_HASH
python login.py             # интерактивно: телефон, код, при 2FA — пароль
```

Скрипт сохранит строку сессии в файл рядом с состоянием (`STATE_DB`), и `repost.py`
возьмёт её оттуда — вручную в `.env` ничего переносить не надо. Это доступ к аккаунту
наравне с паролем: файл не коммитить, не пересылать.

### 3. Узнать точные id чатов

```bash
python repost.py --dialogs
```

Печатает id, тип и название всех ваших чатов. **Id брать отсюда, а не угадывать.**
Заполнить в `.env`: `SRC_CHAT`, `DST_CHAT`, `DST_TITLE_EXPECTED` (точное название цели).
Для локального прогона поставить `STATE_DB=./state.db`.

### 4. Проверка без отправки

```bash
python repost.py --check
```

Печатает, какой чат распознан как источник и какой как цель, и прогоняет все пять
предохранителей. **Глазами убедиться, что в строке «ЦЕЛЬ» стоит нужный канал.**

### 5. Холостой прогон

```bash
python repost.py            # DRY_RUN=true — только список того, что будет отправлено
```

### 6. Боевой запуск

В `.env` поставить `DRY_RUN=false` и запустить снова. Первым уйдёт одно сообщение-
канарейка в целевой канал — проверить, что оно пришло туда, куда нужно. Дальше пойдёт
история от старых сообщений к новым, затем режим ожидания новых.

`HISTORY_LIMIT=20` — это двадцать ПОСЛЕДНИХ сообщений, отправленных по порядку,
от старого к новому. Удобно и для пробы, и как боевой режим, если вся история не нужна.
`HISTORY_LIMIT=0` переносит всё.

## Всё то же самое, но сразу на сервере (без Python на хосте)

Шаги 2–6 можно не делать локально: на сервере есть Docker, и вход в аккаунт
выполняется прямо в контейнере. Виндовые команды выше на Linux не работают —
там `python3`, а активация venv это `source .venv/bin/activate`.

```bash
cd /opt/fanding/funding-service
cp tg-repost/.env.example tg-repost/.env
nano tg-repost/.env          # TG_API_ID, TG_API_HASH; TG_SESSION пока пустой

C="docker compose -f docker-compose.prod.yml --profile repost"
$C build tg-repost

# вход: спросит телефон, код из Telegram, при 2FA — пароль.
# Сессия сама ляжет в том, в /data/session.txt — копировать её никуда не нужно.
$C run --rm --entrypoint python tg-repost login.py

$C run --rm tg-repost --dialogs   # точные id чатов
nano tg-repost/.env               # SRC_CHAT, DST_CHAT, DST_TITLE_EXPECTED
$C run --rm tg-repost --check     # проверить строку «ЦЕЛЬ» глазами
$C run --rm tg-repost             # холостой прогон, DRY_RUN=true
```

`run --rm` подключает тот же том `tg-repost-data`, что и постоянный контейнер,
поэтому привязка и список перенесённого не теряются между запусками.

## Деплой на сервер

Код едет вместе с репозиторием, сервис описан в `docker-compose.prod.yml` под
профилем `repost` — обычный деплой сайта его не поднимает.

```bash
# на сервере
cd /opt/fanding/funding-service
git pull

# .env перепоста не в гите — создать один раз вручную
nano tg-repost/.env        # тот же файл, что локально, но STATE_DB=/data/state.db

# проверка конфигурации, ничего не отправляет
docker compose -f docker-compose.prod.yml --profile repost run --rm tg-repost --check

# боевой запуск (DRY_RUN=false в tg-repost/.env)
docker compose -f docker-compose.prod.yml --profile repost up -d --build tg-repost
docker compose -f docker-compose.prod.yml logs -f tg-repost
```

Состояние живёт в томе `tg-repost-data`, поэтому пересборка контейнера не приводит
к повторной отправке истории. Строка сессии одна на аккаунт: если запустить копию
скрипта локально и на сервере одновременно, Telegram будет ругаться на параллельные
подключения — держать запущенным что-то одно.

Остановить: `docker compose -f docker-compose.prod.yml stop tg-repost`.

## Переменные

Полный список с комментариями — в `.env.example`. Что стоит знать:

| Переменная | Смысл |
|---|---|
| `MODE` | `history` / `live` / `both` |
| `DRY_RUN` | `true` — ничего не отправляется (значение по умолчанию) |
| `DST_TITLE_EXPECTED` | контрольное название цели; пусто = проверка выключена |
| `ALLOW_RETARGET` | разрешить смену пары чатов после первого запуска |
| `HISTORY_LIMIT` | последние N сообщений (`0` — вся история) |
| `HISTORY_MIN_ID` / `HISTORY_SINCE` | с какого сообщения или с какой даты брать историю |
| `FORWARD` | `true` — пересылка с пометкой «Переслано из …»; `false` — копия |
| `SHOW_AUTHOR` / `AUTHOR_TEMPLATE` | подпись отправителя первой строкой (только при `FORWARD=false`); `{name}` — его имя |
| `HISTORY_DELAY_MS` | пауза между отправками, по умолчанию 3000 мс |
| `TG_PROXY_URL` | `socks5://…`; на сервере проекта обязателен |
| `TG_SESSION` / `SESSION_FILE` | строка сессии или путь к файлу с ней (по умолчанию `/data/session.txt`) |

## Если что-то не заводится

**`Attempt 1 at connecting failed: TimeoutError`** — сервер не ходит в Telegram напрямую.
Это ожидаемо: бэкенд проекта по той же причине работает через SOCKS5. Возьмите значение
`TELEGRAM_PROXY_URL` из корневого `.env` и пропишите его в `tg-repost/.env`:

```bash
grep TELEGRAM_PROXY_URL /opt/fanding/funding-service/.env
# TG_PROXY_URL=socks5://host:port  -> в tg-repost/.env
```

Прокси-режим требует пакета `python-socks`, он уже в `requirements.txt`; после правки
`.env` образ пересобирать не нужно, но если менялся `requirements.txt` — нужен `build`.

**Compose печатает свою справку** — потерялся перенос строки при вставке, команда ушла
без подкоманды `run`. Наберите её одной строкой.

**`No matching distribution found`** при сборке — на сервере старая версия файлов,
сделайте `git pull` перед `build`.

**`binascii.Error: Incorrect padding`** — строка сессии в `.env` порвана при вставке.
Не чините её руками: очистите `TG_SESSION`, снова выполните `login.py`, и сессия
сохранится в `/data/session.txt` целиком.

## Тесты

`test_guards.py` проверяет предохранители на подставном клиенте, без сети и без
реального аккаунта: совпадение источника и цели, цель-пользователь, отсутствие прав,
несовпадение названия, смену пары чатов, отсутствие отправок в `DRY_RUN`, отсутствие
дублей при повторном прогоне, срабатывание `send_guard` при подмене цели
чтение сессии из файла (включая отказ на порванной строке)
и подпись автора со сдвигом разметки.

```bash
python test_guards.py      # 16 проверок, код возврата 0 = всё в порядке
```

## Ограничения

- Правки и удаления в источнике не отслеживаются — переносится состояние на момент чтения.
- В альбомах подписи переносятся текстом без форматирования (ограничение группировки
  медиа); у одиночных сообщений форматирование сохраняется полностью.
- Если у автора нет имени (анонимный админ, пост без подписи), строка автора не
  добавляется. Когда подпись не влезает в лимит (4096 у текста, 1024 у подписи к медиа),
  она уходит отдельным сообщением перед контентом.
- Массовая отправка от имени пользователя упирается в лимиты Telegram: при FloodWait
  скрипт ждёт столько, сколько просит сервер, и продолжает. Не снижать `HISTORY_DELAY_MS`
  без нужды.

# tg-repost — перепост из закрытого чата в закрытый канал

Читает закрытый чат вашим **личным аккаунтом** (Telethon/MTProto) и публикует сообщения
в целевой закрытый канал **копией, без пометки «переслано»**. Бот здесь не подходит:
его нельзя добавить в чат, к которому нет доступа.

Переносится: текст с исходным форматированием, фото, видео, документы, голосовые,
альбомы — одной пачкой. Служебные сообщения (вход/выход участников) пропускаются.

## Защита от «улетело не в тот чат»

Это главное требование, поэтому проверок пять, и каждая **останавливает** запуск,
а не пишет предупреждение:

1. **Источник ≠ цель.** Оба чата приводятся к каноническому id (`-100…`) и сравниваются.
   Совпадение id или username — аварийный выход, ни одного сообщения не уходит.
2. **Цель не личный чат.** Промах по id пользователя (в т. ч. «Избранное») отсекается.
3. **Сверка по названию.** `DST_TITLE_EXPECTED` — название целевого канала, как вы его
   видите в Telegram. Открылся чат с другим названием → стоп. Это независимая от id
   проверка: чтобы промахнуться, надо ошибиться дважды и одинаково.
4. **Права на публикацию** в целевом канале проверяются до первой отправки.
5. **Привязка пары чатов.** На первом запуске пара «источник → цель» пишется в state.db.
   Если позже `.env` укажет на другую пару — стоп, пока не выставлен `ALLOW_RETARGET=true`.

Сверх этого: `DRY_RUN=true` по умолчанию (первый запуск ничего не отправляет),
одна «канарейка» в целевой канал перед боевым переносом, и повторная сверка
получателя внутри каждой отправки.

Дубликатов не будет: каждое перенесённое сообщение помечается в SQLite,
перезапуск продолжает с места остановки.

## Порядок запуска (по шагам)

### 1. API-ключи

`my.telegram.org` → API development tools → создать приложение → взять `api_id` и `api_hash`.

### 2. Локально: вход и строка сессии

```bash
cd funding-service/tg-repost
python -m venv .venv && .venv\Scripts\activate      # Windows
pip install -r requirements.txt
cp .env.example .env        # вписать TG_API_ID и TG_API_HASH
python login.py             # интерактивно: телефон, код, при 2FA — пароль
```

Скрипт напечатает строку сессии — вписать её в `.env` как `TG_SESSION`.
Это доступ к аккаунту наравне с паролем: не коммитить, не пересылать.

### 3. Узнать точные id чатов

```bash
python repost.py --dialogs
```

Печатает id, тип и название всех ваших чатов. **Id брать отсюда, а не угадывать.**
Заполнить в `.env`: `SRC_CHAT`, `DST_CHAT`, `DST_TITLE_EXPECTED` (точное название цели).
Для локального прогона поставить `STATE_DB=./state.db`.

### 4. Проверка без отправки

```bash
python repost.py --check
```

Печатает, какой чат распознан как источник и какой как цель, и прогоняет все пять
предохранителей. **Глазами убедиться, что в строке «ЦЕЛЬ» стоит нужный канал.**

### 5. Холостой прогон

```bash
python repost.py            # DRY_RUN=true — только список того, что будет отправлено
```

### 6. Боевой запуск

В `.env` поставить `DRY_RUN=false` и запустить снова. Первым уйдёт одно сообщение-
канарейка в целевой канал — проверить, что оно пришло туда, куда нужно. Дальше пойдёт
история от старых сообщений к новым, затем режим ожидания новых.

Если история большая, разумно сначала прогнать кусок: `HISTORY_LIMIT=20`,
посмотреть результат в канале, потом вернуть `0`.

## Деплой на сервер

Код едет вместе с репозиторием, сервис описан в `docker-compose.prod.yml` под
профилем `repost` — обычный деплой сайта его не поднимает.

```bash
# на сервере
cd /opt/fanding/funding-service
git pull

# .env перепоста не в гите — создать один раз вручную
nano tg-repost/.env        # тот же файл, что локально, но STATE_DB=/data/state.db

# проверка конфигурации, ничего не отправляет
docker compose -f docker-compose.prod.yml --profile repost run --rm tg-repost --check

# боевой запуск (DRY_RUN=false в tg-repost/.env)
docker compose -f docker-compose.prod.yml --profile repost up -d --build tg-repost
docker compose -f docker-compose.prod.yml logs -f tg-repost
```

Состояние живёт в томе `tg-repost-data`, поэтому пересборка контейнера не приводит
к повторной отправке истории. Строка сессии одна на аккаунт: если запустить копию
скрипта локально и на сервере одновременно, Telegram будет ругаться на параллельные
подключения — держать запущенным что-то одно.

Остановить: `docker compose -f docker-compose.prod.yml stop tg-repost`.

## Переменные

Полный список с комментариями — в `.env.example`. Что стоит знать:

| Переменная | Смысл |
|---|---|
| `MODE` | `history` / `live` / `both` |
| `DRY_RUN` | `true` — ничего не отправляется (значение по умолчанию) |
| `DST_TITLE_EXPECTED` | контрольное название цели; пусто = проверка выключена |
| `ALLOW_RETARGET` | разрешить смену пары чатов после первого запуска |
| `HISTORY_LIMIT` / `HISTORY_MIN_ID` / `HISTORY_SINCE` | с какого места переносить историю |
| `HISTORY_DELAY_MS` | пауза между отправками, по умолчанию 3000 мс |
| `TG_PROXY_URL` | `socks5://…`, если Telegram недоступен напрямую |

## Тесты

`test_guards.py` проверяет предохранители на подставном клиенте, без сети и без
реального аккаунта: совпадение источника и цели, цель-пользователь, отсутствие прав,
несовпадение названия, смену пары чатов, отсутствие отправок в `DRY_RUN`, отсутствие
дублей при повторном прогоне и срабатывание `send_guard` при подмене цели.

```bash
python test_guards.py      # 12 проверок, код возврата 0 = всё в порядке
```

## Ограничения

- Правки и удаления в источнике не отслеживаются — переносится состояние на момент чтения.
- В альбомах подписи переносятся текстом без форматирования (ограничение группировки
  медиа); у одиночных сообщений форматирование сохраняется полностью.
- Массовая отправка от имени пользователя упирается в лимиты Telegram: при FloodWait
  скрипт ждёт столько, сколько просит сервер, и продолжает. Не снижать `HISTORY_DELAY_MS`
  без нужды.
